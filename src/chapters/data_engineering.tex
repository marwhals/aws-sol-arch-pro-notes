\subsubsection{Kinesis Data Streams}
\begin{itemize}
    \item Retention between up to 365 days.
    \item Ability to reprocess (replay) data by consumers
    \item Data can't be deleted from Kinesis (until it expires)
    \item Data up to 1MB (typical use case is a lot of "small" real-time data)
    \item Data ordering guarantee from data with the same "Partition ID"
    \item At-rest KMS encryption, in flight HTTPS encryption
    \item Kinesis Producer Library (KPL) to write an optimiser producer application
    \item Kinesis Client Library (KCL) to write an optimised consumer application
\end{itemize}

\subsubsection{Kinesis Data Streams - Capacity Modes}
\begin{itemize}
    \item Provisioned mode:
    \item Choose number of shards
    \item Each shard gets 1MB/s in (or 1000 records per second)
    \item Each shard gets 2MB/s out
    \item Scale manually to increase or decrease the number of shards
    \item You pay per shard provisioned per hour
    \item On-demand mode:
    \item No need to provision or manage the capacity
    \item Default capacity provisioned (4 MB/s in or 4000 records per second)
    \item Scales automatically based on observed throughput peak during the last 30 days
    \item Pay per stream per hour and data in/out per GB
\end{itemize}

\subsection{Firehose Buffer Sizing}
\begin{itemize}
    \item Firehose accumulates records in a buffer
    \item The buffer is flushed based on time and size rules
    \item Buffer Size (ex: 32MB): if that buffer size is reached, it's flushed
    \item Buffer Time (ex: 2 Minutes): if that time is reached, it's flushed
    \item Firehose can automatically increase the buffer size to increase throughput
    \item High throughput => Buffer Size will be hit
    \item Low throughput => Buffer Time will be hit
\end{itemize}

\subsection{Kinesis Data Streams vs Firehose}
\begin{itemize}
    \item Streams
    \item Going to write custom code (producer / consumer)
    \item Real Time (200ms latency for classic, 70ms latency for enhanced fan-out)
    \item Must manage scaling (shard splitting / merging)
    \item Data storage for 1 to 365 days, replay capability, multi consumers
    \item Use with Lambda to insert data in real-time to OpenSearch (for example)
    \item Firehose
    \item Full managed, send to S3, Splunk, Redshift, OpenSearch
    \item Serverless data transformation with Lambda
    \item Near real time
    \item Automated Scaling
    \item No data storage
\end{itemize}

\section{AWS Batch}
\begin{itemize}
    \item Run batch jobs as Docker images
    \item Two options:
    \item Run on AWS Fargate (full serverless offering)
    \item Dynamic provisioning of the instances (EC2 and Spot Instances) - in VPC
    \item Optimal quantity and type based on volume and requirements
    \item No need to manage clusters, fully serverless
    \item You just pay for the underlying resources used.
    \item Example: batch process of images, running thousands of concurrent jobs
    \item Schedule Batch Jobs using Amazon EventBridge
    \item Orchestrate Batch Jobs using AWS Step Functions
\end{itemize}

\subsection{Batch vs. Lambda}
\begin{itemize}
    \item Lambda
    \item Time limit
    \item Limited runtimes (built in runtimes, or Docker images built for Lambda)
    \item Limited temporary disk space

    \item Either using a NAT gateway / instance or using VPC Endpoints for ECS
    \item Unmanaged Computer Environment
    \item You control and manage EC2 instance configuration, provisioning and scaling

\subsection{Amazon EMR - Node types and purchasing}
\begin{itemize}
    \item Master Node: Mange the cluster, coordinates, manage health - long running
    \item Core Node: Run tasks and store data - long running
    \item Task Node (optional): Just to run tasks - usually Spot
    \item Purchasing options:
    \item On-demand: reliable, predictable, won't be terminated
    \item Reserved (min 1 year): cost savings (EMR will automatically use if available)
    \item Spot Instances: cheaper can be terminated, less reliable
    \item Can have long-running cluster or transient (temporary) cluster.
\end{itemize}

\subsection{Amazon EMR - Instance Configuration}
\begin{itemize}
    \item Uniform instance groups: select a single instance type and purchasing option for each node (has auto scaling)
    \item Instance fleet: select target capacity, mix instance types and purchasing options (no Auto Scaling)
\end{itemize}

\section{Redshift}
\begin{itemize}
    \item Redshift is based on PostgreSQL but it's not used for OLTP
    \item Its OLAP - online analytical processing (analytics and data warehousing)
    \item 10x better performance that other data warehouses, scale to PBs of data
    \item Columnar storage of data (instead of row based)
    \item Massively Parallel Query Execution (MPP)
    \item Two modes: Provisioned cluster or Serverless cluster
    \item Has a SQL interface for performing the queries
    \item BI tools such as AWS Quicksight or Tableau integrate with it
\end{itemize}

\subsection{Redshift Continued.......}
\begin{itemize}
    \item Data is loaded from S3, Kinesis Firehose, DynamoDB, DMS......
    \item Based on node type: up to 100+ nodes, up to 16TB of space per node
    \item Can provision multiple nodes, with Multi-AZ only for some clusters
    \item Leader node: for query planning, results aggregation
    \item Computer node: for performing the queries, send result to leader
    \item Backup and Restore, Security VPC / IAM / KMS, Monitoring
    \item Redshift Enhanced VPC Routing: COPY / UNLOAD goes through VPC
    \item Redshift is provisioned, so it's worth it when you have a sustained usage (use Athena if the queries are sporadic instead)
\end{itemize}

\subsection{Redshift - Snapshots and DR}
\begin{itemize}
    \item Snapshots are point-in-time backups of a cluster, stored internally in S3
    \item Snapshots are incremental (only what hass changed is saved)
    \item You can restore a snapshot into a new cluster
    \item Automated: every 8 hours, every 5 GB, or on a scheduled. Set retention.
    \item Manual: snapshot is retained until you delete it.
    \item You can configure Amazon Redshift to automatically copy snapshots (automated or manual) of a cluster to another AWS region
\end{itemize}

\subsection{Amazon Athena - Performance Improvement}
\begin{itemize}
    \item Using columnar data for cost-savings (less scans)
    \item Apache Parquet or ORC is recommended
    \item Huge performance improvement
    \item Use Glue to convert your data to Parquet or ORC
    \item Compress data for smaller retrievals (bzip2 gzipm lz4, snappy, zlip, zstd)
    \item Partition datasets in S3 for easy querying on virtual columns
    \item Use larger files (> 128 MB) to minise overhead
\end{itemize}

\subsection{Amazon Athena - Federated Query}
\begin{itemize}
    \item Allows you to run SQL queries across data stored in relational, non-relational object and custom data sources (AWS or on-premises)
    \item Uses Data Source Connectors that run on AWS Lambda to run Federated Queries (e.g CloudWatch logs, DynamoDB, RDS)
    \item Store the results back in Amazon S3
\end{itemize}
